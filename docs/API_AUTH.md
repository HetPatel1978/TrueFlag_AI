# Browser session persistence

| Endpoint | Behavior |
| --- | --- |
| `POST /api/v1/auth/token` | Existing bearer API login; no browser cookie. Contract unchanged. |
| `POST /api/v1/auth/session` | Browser password login; same validation, throttle and audit. Sets a scoped HttpOnly, SameSite=Strict cookie. |
| `GET /api/v1/auth/session` | Validates the existing JWT and current active account; returns its unchanged token and current role. No expiry extension. Invalid/expired sessions receive 401 and cookie deletion. |
| `POST /api/v1/auth/session/logout` | Clears the scoped cookie, including when credentials have expired. |

- Refresh restores the authenticated workspace after server validation. The default lifetime is **60 minutes from login**; `ACCESS_TOKEN_MINUTES=60` selects the one-hour limit. There is no rolling refresh token or unlimited session. Tokens already issued retain their original expiry; sign out and sign in again after changing the setting.
- Cookies are host-only and restricted to `/api/v1/auth/session`. Nonlocal environments require Secure cookies/HTTPS; local development supports loopback HTTP. Browser session endpoints reject untrusted Origin/cross-site requests.
- Existing protected APIs still require explicit bearer authorization; they never authenticate from the cookie. Tokens stay in JavaScript memory while the page is open, never localStorage/sessionStorage.
- Logout clears in-memory protected state and the cookie. A non-secret pending-sign-out marker prevents an interrupted logout from restoring the prior session on same-tab refresh. Successful logout clears that marker. A copied bearer JWT retains its existing short lifetime; no new global token-revocation claim is made.
- Temporary verification failures hide the workspace and offer retry; they do not silently treat a valid session as anonymous. Hash routes are preserved across refresh. Revoked/inactive users cannot restore a session; role/assignment checks remain server-enforced.
- Tests cover restoration, fixed expiry, forged/expired tokens, deactivation, role changes, cross-site denial, logout and bearer-only compatibility. Real Chromium verified two refreshes without re-login, HttpOnly flags, logout/reload, and cookie expiry against the running application.

## Local-account remembered login

- `LOCAL_PERSISTENT_LOGIN_USERNAME` opts exactly one account into remembered login when `APP_ENV=local`. Empty/unmatched settings and nonlocal deployments retain the regular one-hour session. The local process host configures only its existing review account. Sign in once after enabling the option; old cookies are not silently upgraded to indefinite authority.
- Password-authenticated browser login creates an opaque, random HttpOnly/SameSite=Strict cookie. Its secret is hashed in an immutable `auth.remembered_session.created` audit grant; only the raw cookie is sent to the browser. An appended revocation event records sign-out. No schema migration or scientific-service change is required. This reuses the existing durable audit ledger for this restricted development mode, not an enterprise identity/session platform.
- The browser cookie has a **365-day lifetime renewed on successful restoration**, subject to the browser's retention policy. The grant has no fixed server-side time expiry. Thus normal refreshes and browser/application restarts preserve login; deleting cookies, private browsing or very long inactivity beyond browser retention requires signing in again. Do not claim a browser can retain credentials literally forever.
- Restoration independently checks the current account, deployment/account eligibility, credential/role/signing-key stamp and grant revocation before issuing another expiring one-hour bearer token. The frontend renews before expiry and on returning to an expired tab. API access still requires explicit bearer authorization; no credential is stored in localStorage or sessionStorage.
- Remembered bearer tokens bind their grant via `sid`. Every authenticated use checks that grant and current credentials. Logout revokes the grant and its issued tokens; role/password changes, account disablement, signing-key rotation or disabling the local setting deny further access. Grant locking serializes restore/logout; failed revocation rolls back and does not falsely confirm sign-out.
- Renewal failure hides the workspace and offers retry; logout aborts in-flight renewal. Ordinary expiry and evidence snapshot/lease deadlines remain enforced. A dedicated indexed session store, cleanup policy, device administration and production refresh-token design are required before expanding this local-only mode. Preserve the audit grants/revocations while remembered login is in use.
- Verified November 18, 2026: Linux/PostgreSQL auth/foundation/remembered-login tests **46 passed** (including concurrent restore/logout and revocation rollback); Windows/SQLite **45 passed, 1 PostgreSQL-only skip**; React **131 passed**. Real Chromium verified automatic renewal using a renderer-only clock simulation, persistent-profile browser-process restart, refresh, absence of web-storage credentials, and rejection of both cookie and bearer replay after logout. Host, database, worker and evidence clocks were not changed. Ruff, ESLint, Prettier and TypeScript/Vite build passed. No database migration, ML change or provider call was required.
